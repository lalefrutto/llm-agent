# Evals — как оцениваем LLM и как оцениваем агентную систему

Это два разных вопроса, и в отчёте (ТЗ, п. Evals) их специально не
скипаем — путают их часто, поэтому явно разводим.

## 1. Оценка самой LLM (до того, как она стала частью агента)

Проверяется на этапе выбора модели (`config/models.yaml`), до
интеграции в граф.

| Метрика | Как измеряется | Инструмент/среда |
|---|---|---|
| Инструктивность | Rubric-based scoring на наборе промптов с чёткими критериями | Локальный harness + LLM-as-judge (более сильная модель или человек) |
| Склонность к галлюцинациям | Faithfulness: модель отвечает по данному контексту, проверяем, не добавляет ли фактов вне контекста | Адаптированный протокол TruthfulQA/RAGAS-style faithfulness |
| Качество tool-calling | % ответов с валидным JSON под заданную tool schema | `evals/run_evals.py::score_tool_calling` |
| Использование контекстного окна | Needle-in-a-haystack на разной длине контекста (что влияет на качество long-context агентных сценариев) | Кастомный скрипт, синтетические длинные контексты |
| Скорость | Токенов/сек, latency до первого токена | Замер через `llm_client.py` на локальном железе |

## 2. Оценка агентной системы в целом (и конкретно нашей)

Это про поведение графа, а не отдельной модели.

| Метрика | Как измеряется |
|---|---|
| Task success rate | Доля задач из `evals/dataset.jsonl`, для которых финальный ответ проходит проверку (exact/rubric/judge) |
| Routing accuracy | Для задач с известным "правильным" под-агентом — совпадение `route` с ожиданием |
| Step efficiency | Среднее число шагов графа на задачу vs эталонное минимальное число |
| Critic catch rate | На adversarial-подмножестве с намеренно испорченным результатом executor — доля случаев, когда critic вернул `revise/reject` |
| Memory correctness | Двухходовые сценарии "сообщил факт → обновил факт → спросили" — проверяем, что вернулась актуальная версия |
| Guardrail compliance | Adversarial-промпты на побег из sandbox / запрос необратимых действий — доля корректно заблокированных |
| Стоимость и латентность на завершённую задачу | Из трейсов Langfuse, агрегация по `evals/dataset.jsonl` прогону |

## Среды запуска

- **CI/локально (разработка):** `pytest evals/` — детерминированные
  проверки (guardrails, memory correctness, routing на фиксированных
  seed-примерах).
- **Пред-релизный прогон:** полный `evals/dataset.jsonl` с LLM-as-judge
  для открытых критериев — вручную или по расписанию.
- **Continuous monitoring в проде:** сэмплирование N% реального
  трафика в Langfuse eval-пайплайн (см. `observability/README.md`) —
  ловим дрейф качества, которого нет в статичном датасете.

## Запуск

```bash
pip install -r ../requirements.txt
python run_evals.py --dataset dataset.jsonl
```
