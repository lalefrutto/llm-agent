## Рубрика инструктивности (0..1 на кейс, среднее по модели)

- JSON-решения роутера: валидный JSON / все ключи action+reasoning+subtask / action из разрешённого списка / subtask заполнен при делегировании и нет лишних полей при answer_directly.
- JSON критика: валидный JSON / ключи verdict+issues+suggested_fix / verdict из списка / issues — непустой список строк.
- Свободный текст: непустой / на русском (SOUL.md) / без служебного JSON / не оборван.
- Tool-calling: 1.0 — нужный инструмент + аргументы по схеме; 0.5 — вызов есть, но не тот/невалидный; 0 — вызова нет.

## Методологические замечания

- **`json_mode` обязателен.** Без `response_format=json_object` (см. `llm_client.py`)
  routing/critic-кейсы у всех моделей уходили в 0% — модели отвечали текстом вместо
  JSON. Все цифры выше получены с включённым grammar-constrained JSON.
- **Critic catch = 0/1 у всех четырёх.** Все модели находят необработанное деление на
  ноль, но возвращают `reject`, а датасет ждёт `revise`. Это не различие моделей, а
  неоднозначность промпта критика — после прогона в `prompts/subagent_critic.md`
  добавлен явный критерий revise vs reject (live-evals в `run_evals.py` идут уже с ним).
- **Latency первого кейса (t01: 5–9 с) — это cold load модели**, остальные вызовы
  1–2 с. Отдельный замер: переключение между двумя 7–8B моделями на 8 GB VRAM стоит
  **5–7 с** на каждый swap (warm 1.7 с vs cold 6.5–8.5 с; `ollama ps` показывает, что
  резидентна только одна модель).
- Hallucination rate 0/5 у всех — кейс t10 с явной инструкцией "только по тексту"
  оказался слишком лёгким для 7B+; для дифференциации нужен более широкий
  faithfulness-набор (см. ограничения в отчёте).

## Итоговая рекомендация

**1 место — `hermes3:8b-llama3.1-q4_K_M` → primary для всех ролей графа
(orchestrator, researcher, executor, critic) и для извлечения фактов в Mem0.**
Единственная модель с 1.00 по рубрике инструктивности и 3/3 routing accuracy —
в т.ч. единственная, кто делегирует арифметику executor'у (t01), как требует
`system_prompt.md`, а не считает "в уме". Tool-calling 3/3 с корректными аргументами
по схемам `agent/tools/`. Скорость 41.8 tok/s, avg latency 3.04 с — на уровне qwen2.5
(3.40 с); старый вывод "hermes3 вдвое медленнее" был артефактом swap'ов моделей.

**2 место — `qwen2.5:7b-instruct-q4_K_M` → резервная / critic при VRAM ≥ 12 GB.**
Tool-calling и JSON 100%, самый высокий tok/s среди 7–8B (45.1), но два серьёзных
минуса: (а) routing 2/3 — арифметику отвечает сама (`"result": 810` прямо в
routing-JSON вместо делегирования); (б) **дрейф в китайский язык** в 2 кейсах из 11
(t06 — весь ответ на китайском, t07 — мусор `URLException: 过长的字符串…` внутри
issues). Для русскоязычного ассистента это дисквалифицирует её как primary.
Изначальный выбор qwen2.5 primary в `config/models.yaml` данными **не подтвердился**
— конфиг обновлён.

**3 место — `llama3.1:8b-instruct-q4_K_M` → comparison baseline, в проде не
используется.** Инструктивность 0.97, память и tool-calling ок, но routing 1/3:
на t02 ("что нового у Ollama") ответила `answer_directly` и **выдумала** новости
вместо делегирования researcher'у — ровно та галлюцинация, от которой должен
защищать роутер.

**4 место — `phi3.5:3.8b-mini-instruct-q4_K_M` → не использовать.** Ollama-шаблон
модели не поддерживает tools (`400: does not support tools`, 3 errors), routing 1/3
(на t01 вернула `{"result": 765}` — и неверно, и не по схеме), JSON 80%. Быстрее всех
(66.7 tok/s), но на 8 GB VRAM это преимущество съедается swap'ом (+5–7 с) при
переключении с основной модели — поэтому от идеи "дешёвые вызовы для memory
extraction на phi3.5" отказываемся: Mem0 тоже работает на hermes3.

Общий принцип, который дали цифры: **на 8 GB VRAM выгоднее одна резидентная модель
на все роли, чем "правильная" модель на каждую роль** — любое разведение ролей по
моделям добавляет 5–7 с на каждый переход между узлами графа.
