# Система организации памяти — обоснование выбора

## Итоговое решение

- **Краткосрочная память:** буфер диалога + rolling summarization,
  персистентность через **LangGraph checkpointer** (SQLite для
  разработки / Postgres в проде), скоуп — `thread_id`.
- **Долгосрочная память:** **Mem0** как основной слой (fact-level
  memory с операциями ADD/UPDATE/DELETE/NOOP и многоуровневым
  скоупом user/session/agent) поверх векторного хранилища **Qdrant**.
- **Путь апгрейда:** Mem0 умеет работать с графовым бэкендом; при
  росте требований к многошаговому/темпоральному reasoning —
  подключить **Graphiti** как graph store вместо/поверх Qdrant без
  смены API на уровне агента.

## Почему НЕ классический RAG (chunk + embed + top-k similarity)

Классический RAG подходит для статичной базы знаний (документация,
FAQ), но плохо ложится на **память агента о пользователе и диалоге**
по нескольким причинам:

1. **Нет модели противоречий.** RAG просто добавляет новый чанк;
   если пользователь сообщил "живу в Москве", а через месяц —
   "переехал в Питер", top-k similarity может вернуть оба факта без
   разрешения конфликта. Агенту-памяти нужна операция UPDATE, а не
   append-only.
2. **Нет темпорального измерения.** Векторная близость не учитывает
   "когда это было сказано" и "актуально ли ещё" — для вопросов
   "что изменилось с марта" plain RAG не даёт естественного способа
   ответить.
3. **Top-k similarity ≠ релевантность для личной памяти.** Для
   персонализации важны recency и importance-weighting (частота
   упоминания, явная пометка "запомни это"), а не только косинусная
   близость эмбеддинга.
4. **Плохая масштабируемость по шуму.** С ростом истории диалогов
   растёт число похожих, но неактуальных чанков — retrieval
   деградирует без консолидации/забывания.
5. **Нет multi-hop связей.** Вопрос "с кем пользователь работает над
   проектом X и какие у них дедлайны" требует связывания сущностей
   (проект → люди → дедлайны) — плоский набор чанков это не
   моделирует; для этого нужен граф знаний.

## Сравнение рассмотренных вариантов

| Инструмент | Сильные стороны | Слабые стороны / почему не выбран как основной |
|---|---|---|
| **Mem0** (выбран) | Готовые ADD/UPDATE/DELETE операции, multi-level scope (user/session/agent), self-host или cloud, большое community (53k★) | Решения об update принимает LLM-вызовом → доп. латентность/стоимость на каждый turn; из коробки без графового бэкенда теряет multi-hop reasoning |
| **Graphiti** | Темпоральный граф знаний, инкрементальные апдейты, задуман как production-замена RAG | Требует Neo4j/graph-инфраструктуру — выше операционная сложность для соло-проекта в рамках курса; выбран как **путь апгрейда**, не стартовая точка |
| **Letta (MemGPT)** | Саморедактируемые блоки памяти, готовый агентный рантайм | Это целый агент-фреймворк, а не только память — конфликтует с выбором LangGraph как основного фреймворка оркестрации |
| **Zep** | Готовый drop-in memory layer, суммаризация истории | Функционально во многом пересекается с Mem0, меньше звёзд/экосистема (4.5k★) |
| **LangMem** | Нативная интеграция с LangGraph store | Меньше возможностей многоуровневой памяти "из коробки" по сравнению с Mem0 |
| **memU** | Память как файловая система, очень экономична по токенам | Заточен под 24/7 проактивных агентов; ретривал менее развит для точечного fact-recall |
| **Cognee** | Vector + graph + когнитивно-научный подход | Моложе, выше риск интеграционных проблем в сроки курсового проекта |
| **PageIndex, LlamaIndex, RAGFlow, SuperMemory** | Отличны для RAG **по документам** (иерархическая навигация, ingestion) | Это retrieval-движки для базы знаний, а не память агента о пользователе/диалоге — используются нами отдельно, как источник знаний для инструмента Researcher, а не как `memory/` |

## Недостатки выбранного решения (честно)

- Дополнительный LLM-вызов на решение об ADD/UPDATE увеличивает
  латентность (~1 доп. inference на turn) — компенсируется тем, что
  вызов идёт на ту же локальную легковесную модель.
- Без графового бэкенда теряем часть multi-hop reasoning — заложен
  явный путь апгрейда на Graphiti, а не тупиковое решение.
- Self-hosted Mem0 + Qdrant — два дополнительных сервиса в
  docker-compose, что усложняет деплой по сравнению с "просто вектор
  в SQLite".
